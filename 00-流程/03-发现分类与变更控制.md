# 03 · 发现分类与变更控制

> **一句话**：规定"检查发现"怎么分类、"冻结"怎么定义、"冻结之后"怎么改。
> **地位**：与 `01-开发流程.md` 同级，是**机制 2 / 机制 3** 的细化。
> **依据**：用户 2026-09-19 授权确立；来源 = 产品经理（需求侧）与架构师（设计层）两份独立提案的汇编
> **谁能改**：AI 只能在 `../30-待裁决/` 提建议；改动本文件须用户裁决

---

## 一、发现分类器（每个发现必须且只能归一类）

> **一句话**：只有 D 类能卡住冻结；C / I / Q 各有出口，不回头污染当前层。

| 类 | 定义 | 处置动作 | 卡不卡冻结 | 裁决人 |
|---|---|---|---|---|
| **D 缺陷** | 违反某条**已冻结**的条目 | 回到该条目，修到验收通过 | **卡** | 用户（确认验收） |
| **C 变更** | 冻结条目**之外**的新要求 | 开变更单，挂起 | 不卡 | 用户 |
| **I 改进** | 现行为可接受，想更好 | 进 `../70-Backlog/` | 不卡 | 用户（排期时） |
| **Q 未知** | 信息不足，判不了 | 转成显式假设，进 `../40-假设台账/` | 不卡 | 用户 |

### 为什么 C / I / Q 不计入"未收敛"

> **一句话**：它们不是"现有条目的错"，而是"新信息"；若计入，则每轮探索都会生产未收敛项 ⇒ 永远无法冻结。

这正是上一轮的病根：把"还想得到什么"当成"还得修什么"，于是发现量 ≡ 工作量，退出条件（当时定的"连续 2 轮无新增即停"）**永远无法满足**——因为每一轮都在做加法。

---

## 二、冻结动作的定义

> **一句话**：冻结 = 条目冻结 + 边界冻结 + 未知登记 + 打开变更通道；四件套同出才算定稿。

一次冻结动作必须**同时**产出：

| # | 产出 | 作用 | 落点 |
|---|---|---|---|
| 1 | 已冻条目清单 | 作为**唯一对照物** | `../10-基线/` |
| 2 | **明确不做清单** | 划边界，防同一问题换皮再冒出来 | 该基线文件的附录节 |
| 3 | 未决假设清单 | 带未知前进的凭证 | `../40-假设台账/` |
| 4 | 空变更单 | 冻结后唯一入口 | `../50-变更单/` |

**冻结后的修改规则**：改动已冻结内容的**唯一通道**是变更单。口头提出的新要求一律记为 **C 类**，不予执行。

---

## 三、变更单模板

> **一句话**：一处改动一张单；驳回的单也留档。

文件名：`CR-NNN-短名.md`（NNN 三位流水号，短名 ≤ 8 字）

| 字段 | 填写要求 |
|---|---|
| 编号 | `CR-001` 形式，唯一不复用 |
| 为什么改 | 触发原因（对应哪个 C 类发现，或用户的哪条指令） |
| 改什么 | 一句话说清改动本身 |
| 影响哪些已冻条目 | **逐条列出受影响条目的 ID** |
| 代价 | 返工范围、需重跑哪几层的闸门 DoD |
| 裁决 | 用户勾选：批准 / 驳回 |
| 裁决日期 / 裁决人 | 必填 |

**处置**：批准 ⇒ 目标层升版本，并**重跑该层及其下层**的闸门 DoD；驳回 ⇒ 记入 `../70-Backlog/`，**不删除**（防同一建议反复提出）。

### 版本号规则（2026-09-19 补，此前只有"升版本"三个字、无规则）

> **一句话**：每层首次冻结为 **v1.0**；此后每次批准变更 **+0.1**。

| 规则 | 说明 |
|---|---|
| 首次冻结 | **v1.0** |
| 每次批准的变更单 | **+0.1**（如 v1.0 → v1.1） |
| **内容不兼容的改动**（推翻已冻条目、改语义） | **+1.0 并重置小号**（如 v1.3 → v2.0），且必须在冻结物元信息里写明**推翻了哪条** |
| 版本号写在哪 | 冻结物的**页眉**与**冻结元信息**节 |
| 与 git 的关系 | 每次冻结/升版，在 git 打 tag：`<层名>-v<版本>`（如 `S-1-v1.0`）—— **建仓后适用** |

> ⚠️ 版本号**只增不减**；有单才升版，**无单不得改版本号**。

### 冻结元信息的更新规则（2026-09-19 补）

> **一句话**：**元信息字段（版本 / 冻结日期 / 闸门轮次 / 四件套）随变更单自动更新，不单独开单**。

| 规则 | 说明 |
|---|---|
| **算哪一类** | 元信息**不属于"已冻条目"**，是"描述这份冻结件自身状态"的字段 |
| **更新时机** | 每次变更单执行的**收尾步骤**里一并刷新 |
| **为什么要单独说明** | 否则每开一张变更单，都要再开一张"更新元信息"的单 —— **循环依赖，显然不合理** |
| **边界** | 一次变更单**只能刷新它自己引起的元信息变化**；不得借刷新之名改动条目内容 |

> ⚠️ 2026-09-19 实际发生：元信息停在 `CR-003` 时代、未跟上 `CR-004`~`CR-006` 与第 6~9 轮 ⇒ 由**第 10 轮（引用可达性检查）**查出。

## 四、假设台账字段

> **一句话**：Q 类未知不在当轮解决，转为假设登记并**设定最晚验证点**，允许"带着未知前进"。

| 字段 | 填写要求 |
|---|---|
| 编号 | `AS-NNN`，唯一不复用 |
| 假设内容 | 一句话（例："多台设备的型号一致"） |
| 若不成立的影响 | 会影响哪些条目 / 哪一层 |
| **最晚验证时点** | 指定到具体层或事件（例："在冻结 S2 之前"） |
| 验证方式 | 询问用户 / 原型验证 / 骨架验证 |
| 状态 | ⏳ 待验证 / ✅ 已验证（附结论） / ❌ 已推翻 |

**到期规则**：假设到验证时点仍未验证 ⇒ **自动升级**为 `../30-待裁决/` 的阻塞条目，**不得无声跳过**。

---

## 五、从"发现"到"动作"的完整路径

> **一句话**：一个发现进来，先判类别再走分支；**不许直接跳到"那就改设计吧"**。

| 发现属于 | 走哪条路 | 是否立刻返工 |
|---|---|---|
| 违反某条已冻条目 | **D** → 修该条目 → 重跑本层闸门 | **是** |
| 已冻范围之外的新要求 | **C** → 开变更单 → 挂起待裁 | 否 |
| 不满足但可接受 | **I** → Backlog | 否 |
| 信息不足判不了 | **Q** → 假设台账（带验证时点） | 否 |
| 要把 C / I / Q 升级为 D | **必须经用户裁决**（走变更单） | 视裁决结果 |
