## 原则 1 · 配置开放原则

> **一句话**：凡是**阈值、上限、周期、开关**这类可调的东西，**默认都开放给用户配置**，不要硬编码。

### 来源（用户原话）
> 「我做软件就是喜欢**只要能开放的设置全部给用户开了**」
> 「记住原则：**能给用户开设置就开上**，这个可以写在原则文档上」

### 该开 vs 不该开（边界，防止走偏）

| ✅ **该开放的** | ❌ **不该开放的** |
|---|---|
| 数值阈值（掉线阈值、误差超阈值） | **架构性选择**（进程模型、通信协议） |
| 周期 / 频率（状态刷新率、UI 刷新率、心跳） | **安全约束**（急停必须本地优先 —— 不可关） |
| 上限（设备台数、日志保留量） | **状态机的合法迁移**（B-017a 已定） |
| 功能开关（某能力启停） | 已被 S-1 冻结的范围边界 |

### ⚠️ 关键约束：开放配置**不得牺牲架构**

| 要求 | 说明 |
|---|---|
| **集中管理** | 配置**一处定义、一处加载**；不得散落成满地 `if/else` |
| **有默认值** | 每个配置项都必须有默认值（开箱即用） |
| **有取值范围** | 非法值要有明确处理（拒绝 + 提示，或回退默认） |
| **安全项不可关** | 安全相关行为不得通过配置关闭（如急停本地优先） |
| **可测试** | 配置加载 / 非法值处理要能单测 |

### 落地形式
- **需求层面**：`REQ-INF-006`（参数可配置，全局约束）
- **实现层面**：配置模块 + 配置文件 + 设置界面（UI）
