## 表二 · 新增问题清单

### F1 · E1「依据」未覆盖其列出的"编程 / 校验 / 确认"交互 【C】

- **问题**：E1 交互内容列了"操作：编程 / 校验 / 下发 / 启停 / 确认"，但依据栏只有 `REQ-UI-001 · REQ-UI-003 · REQ-DEV-001`。
- **证据原文**：
  - `20-设计/S1-架构基线草稿.md` §14.2 表：「**E1｜操作员｜…操作：编程 / 校验 / 下发 / 启停 / 确认｜图形界面｜双向｜`REQ-UI-001` · `REQ-UI-003` · `REQ-DEV-001`**」
  - `10-基线/S0-需求基线.md`：编程有 `REQ-PRG-001`（程序可新建/打开/保存）、`REQ-PRG-002`（基元增删改）；校验有 `REQ-CHK-001~005`；确认有 `REQ-RUN-010`（作业前强制确认）、`REQ-DEV-005`（批量下发二次确认）、`REQ-ALM-002`（两次确认）。
- **为什么是问题**：当前依据只能支撑"看 / 下发 / 启停"（UI-001/003、DEV-001），对明确列出的"编程 / 校验 / 确认"三类交互缺乏需求级支撑，依据栏与交互内容不自洽。
- **建议**：E1 依据补 `REQ-PRG-001 · REQ-PRG-002 · REQ-CHK-001~005 · REQ-RUN-010 · REQ-DEV-005 · REQ-ALM-002`，使交互内容与依据一一对应。

### F2 · "时间戳单一来源"被误归到 REQ-DB-005（§14.2 E5 与 §14.5 约束3） 【C】

- **问题**：E5 依据与第 3 条硬约束都把"时间戳单一来源"的满足证据挂到 `REQ-DB-005`，但 REQ-DB-005 是"数据标准化（字段格式统一）"，与时间源无关。
- **证据原文**：
  - `20-设计/S1-架构基线草稿.md` §14.2：「**E5｜系统时钟｜…单向（读）｜`REQ-LOG-003` · `REQ-DB-005`**」
  - `20-设计/S1-架构基线草稿.md` §14.5：「**3｜E5 时间戳来源单一 ⇒ 所有记录的时间从一个口取｜满足 `REQ-DB-005` 数据标准化**」
  - `10-基线/S0-需求基线.md` `REQ-DB-005` 定义：「**数据标准化（统一字段格式）**……① 关键数据对象各有唯一定义 ② 同一含义不出现两种字段名 ③ 状态字段复用 8 态枚举 ④ 可用单测校验」——全篇未涉"时间戳来源"。
  - 真正对应"每条记录带时间戳"的是 `REQ-LOG-003`；"唯一写者 / 单来源"是 S-1/S0 的 `§五 硬约束②（data/log 唯一写者）`；时间口径本身仍在 `AS-006` 待定。
- **为什么是问题**：依据错配。若 #5/#6 设计者据此溯源，会误以为 REQ-DB-005 已覆盖时间源，实际未覆盖（AS-006 口径仍待定），可能让"单一时间源"在下游落空而无人察觉。
- **建议**：§14.2 E5 依据改为 `REQ-LOG-003 · §五硬约束② · AS-006`；§14.5 约束3 改为"满足 `REQ-LOG-003` + `§五硬约束②（data/log 唯一写者）`"，并注明 AS-006 口径待定。
- **说明**：已知重复清单中的"假核对"指 #5/#6 依赖边表，本处为 #4 §14.2/§14.5 的具体 REQ 错配，非同类投影，故单列。

### F3 · data/store 取时间戳来源未在边表体现，约束3 的"所有记录从一个口取"断链 【C】

- **问题**：约束3 要求所有记录走单一时间源，但依赖边表只有 `data/log -> E5`，`data/store` 无任何 E5 边，单一来源的传递关系在图中断链。
- **证据原文**：
  - `20-设计/S1-依赖边表.txt` D 层：「`data/log -> E5 | D | protocol | §14.2 E5(时间戳来源)`」；`data/store` 出边为 `data/store -> infra/lifecycle`、`data/store -> E4`，入边来自 dashboard/execution/error/stats/device/replay，无任一 E5 边。
  - `20-设计/S1-接口清单.md` `data/store` 职责含"记录持久化（REQ-DB-001/002/003/005）"、含"时间戳统一（REQ-DB-005 单位统一）"，但 `ITimestampSource`（"时间戳唯一来源"）仅定义在 `data/log`。
- **为什么是问题**：约束3 声称"所有记录从一个口取"，data/store 既写带时间戳的记录又无对应边，#6 运行时视图无法据此验证单一来源是否真正贯通。
- **建议**：在边表补 `data/store -> E5`（D 层，复用 data/log 的 `ITimestampSource`），或显式说明"data/store 接收由调用方 / data/log 预置时间戳的记录"，并在接口清单 data/store 节注明时间戳来源。

### F4 · E6 方向标"单向"对开发期实体有误导风险 【I】

- **问题**：E6 类型已是"开发期（不参与运行时）"，却用运行期数据流用语"单向"标注方向。
- **证据原文**：`20-设计/S1-架构基线草稿.md` §14.2：「**E6｜构建 / 开发环境｜开发期（不参与运行时）｜…｜单向｜`REQ-INF-001` · `REQ-INF-008` · `B-027` · `S-1 §二`**」
- **为什么是问题**："单向"是运行期数据流方向用语，E6 本质无运行期数据流，读者易将其纳入运行期数据流分析。
- **建议**：方向改为"不适用（开发期；运行期无数据流）"，或保留但加注"仅 1 条 D 边、运行期不参与"。

### F5 · §14.2 未说明 SQLite / Modbus库 / Git远端 为何不算独立实体 【I】

- **问题**：实体表只列 7 个（E1~E7），未解释本次审查也专门比对的 4 个候选为何被吸收。
- **证据原文**：`20-设计/S1-架构基线草稿.md` §14.2 实体表与自查（`grep -cE '^\| \*\*E[0-9]'` ⇒ 期望 7）；其 E4 交互内容含"SQLite 库"、E2 协议"对外语义 = Modbus TCP"、E6 交互内容含"Git + 远端仓库"。
- **为什么是问题**：吸收本身合理（SQLite/日志文件→E4 文件 API；Modbus库→内部 `comm/modbus` 模块、对外归 E2；Git远端→E6），但 §14.2 未写明"为何不单列"，审查者会重复提出同样疑问。
- **建议**：在 §14.2 表下补一行注记："SQLite / 日志文件 → E4（文件 API）；Modbus 库 → 内部 `comm/modbus`，对外归 E2；Git 远端 → E6；均不单列"。

### F6 · E4 依据对"读配置 JSON"支撑偏弱 【I】

- **问题**：E4 交互内容含"读：配置 JSON"，但依据未列最直接支撑。
- **证据原文**：`20-设计/S1-架构基线草稿.md` §14.2：「**E4｜…读：配置 JSON｜…｜`REQ-DB-001` · `REQ-INF-006` · `REQ-LOG-009`**」；`S0-需求基线.md` `REQ-DB-004`="选型落地：SQLite（业务数据）+ JSON（配置）"、`REQ-PRG-001` 覆盖程序文件读写；`REQ-INF-006` 是"参数可配置（全局约束）"而非"读配置 JSON 文件"。
- **为什么是问题**："读配置 JSON"最直接支撑是 `REQ-DB-004`（JSON 配置）+ `REQ-PRG-001`（程序文件），当前依据未列，存在依据与交互内容错配。
- **建议**：E4 依据补 `REQ-DB-004 · REQ-PRG-001`，或将 `REQ-INF-006` 注明"配置集中管理"。

### F7 · §14.4 可补 S-1 §四 预留⑨「不做目标平台构建」边界 【I】

- **问题**：§14.4 自称"只引用 S-1 已冻结的不做 / 预留 / 边界条目"，但只引用了不做①②③④ + §7 B-007 + §五，未引用显式"不做构建"的预留⑨。
- **证据原文**：`20-设计/S1-架构基线草稿.md` §14.4 六行；`10-基线/S-1-立项声明.md` §四 预留⑨="Linux / macOS 多平台构建与安装包——不做目标平台构建"。
- **为什么是问题**：非错误，仅完整性可加强（预留⑨ 是明确的"不做构建"边界）。
- **建议**：视需要补一行"不做跨平台目标构建 | S-1 §四 预留⑨"。

### F8 · §14 内无"L3"违规，但接口清单 L1/L2/L3 为渲染精度同形词，外部暴露需防混 【I】

- **问题**：§14 自身合规，但同项目接口清单出现的"L1/L2/L3"与禁止的成熟度"L3"字形相同。
- **证据原文**：`20-设计/S1-架构基线草稿.md` §14 全章无禁止性"L3"、ISO ①②③④ 为域编号；`20-设计/S1-接口清单.md` `setLodPolicy(...) // 渲染精度分级（REQ-3D-010；L1/L2/L3）`——此为 LOD 渲染档（REQ-3D-010），非数字孪生成熟度 L3。
- **为什么是问题**：§14 无需改；但若将来 README/面试直接移植该注释，可能被误读为成熟度 L3，违反 S-1 §五。
- **建议**：接口清单中 LOD 档位注释加前缀"渲染"（如"渲染 L1/L2/L3"）以与成熟度 L3 区分。

## 表三 · 结论

**#4 能不能批？** —— **可以批（无 D 类阻塞）**。§十四 的外部实体完整性、方向（除 E6 措辞）、边界只引用不自拟、四域落位、与边表 E1~E7 的一致性、术语纪律、格式修复均经核对成立。

**需修（C 类，建议冻结前修）：**
1. **F2**：§14.2 E5 与 §14.5 约束3 的"时间戳单一来源 ⇒ 满足 REQ-DB-005"为误配，应更正为 `REQ-LOG-003` + `§五硬约束②` + `AS-006`（最重，影响 #5/#6 溯源）。
2. **F1**：E1 依据未覆盖其列出的"编程 / 校验 / 确认"，补 `REQ-PRG-*` / `REQ-CHK-*` / `REQ-RUN-010` / `REQ-DEV-005` / `REQ-ALM-002`。
3. **F3**：`data/store` 取时间戳来源未在边表落点，补 `data/store -> E5` 或显式说明，使约束3 贯通。

**可不改（I 类打磨）：** F4（E6 方向措辞）、F5（吸收说明）、F6（E4 依据）、F7（预留⑨ 补引）、F8（LOD 同形词防混）。

**最重的 3 条**：F2（时间源误挂 REQ-DB-005）> F1（E1 依据缺编程/校验/确认）> F3（data/store 时间源断链于边表）。

**缺什么才能更稳**：C 类 3 条修正后，#4 可作为正式上下文视图冻结；其中 F2/F3 直接关系"单一时间源"这一硬约束能否被 #5/#6 真正继承，建议优先处理。
