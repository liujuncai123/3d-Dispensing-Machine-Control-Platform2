## 表二 · 新增 D / C 清单（逐条证据 + 实测数据）

> 归类说明：S1 当前**未冻结**，严格意义上没有"已冻结条目"可供 D 类触犯；下表 7 条均为对「方法草案」的 **C 类变更请求**（须改方法才可采用）。若把"方法草案的完成判据"视为待冻结承诺，则轮 12（C-12a）最接近"伪判据"风险， borderline D，文中已注明。

### C-8a（轮 8）· #5 与 #18 无交接物，逻辑边表 ≠ 编译期依赖图
- **证据原文**（`20-设计/S1-架构基线草稿.md`，§17.5 数据流）：
  > "→ core/device(★落成唯一事实源) → **infra/eventbus** → **app/scene3d**(画) + **app/dashboard**(显示表)"
  > 同文件 §十二 A4："**走 `infra/eventbus` 事件通道** —— 底层有事往上通知，`core` 绝不依赖 `app`"
- **证据原文**（被审方法草案）："依赖分四层：A 层·静态依赖（只装 1 类：【使用期依赖】← 唯一进 DAG 的层）…… 产出 5 步：边表 → `check-deps.py`…"——全程未出现"编译期 / `#include` / 链接 / CMake target"如何由 #5 供给 #18。
- **实测数据**：
  - §17.5 数据流：A 层 **8** 跳、B 层(经 `infra/eventbus`) **3** 跳、外部 E2 **2** 跳。
  - 编译期依赖 `业务/UI → infra/eventbus` 的使用者（§17.5 实证）≥ **3** 个模块：`core/device`(发布)、`app/scene3d`(订阅)、`app/dashboard`(订阅)；§十二 A4"底层有事往上通知"还隐含 `core/*` 多发布者。
  - 这 **3+** 条编译期边属 B 层，被方法草案明确"不进 DAG"，故 **#5 的 DAG 里完全看不到它们，但 #18 划 CMake target 时必须把它们当真实链接依赖**——#5 既没给、也没告诉 #18 去哪取。
  - #18 的下游消费者合计 **4** 个（#18 自身、S2、#6、#5 脚本）。

### C-9a（轮 9）· 无边→接口映射规则 / 无接口粒度原则归属
- **证据原文**（被审方法草案）："边表列（机器可读，唯一权威源）：使用者 → 被使用者 : 出处"；完成判据只要求"每条边有「出处」字段"——**没有任何一句说"这条边将来怎么变成 S2 接口"**。
- **证据原文**（`00-流程/01-开发流程.md`，S2 行）："每条接口 = 签名 + 前置/后置条件；**调用方与提供方描述逐条一致**；有可跑 stub"。S1.5 行："**骨架跑通后，把'定不下来的问题'改写成『已暴露的确定事实』**…… 只有确定事实进 S2"。
- **实测数据**：§五 11 行数据类 → 方法称抽 **14** 条候选；§17.5 A 层 **8** 跳；两者并集（扣 3 处重叠）预期唯一边 ≈ **19** 条。每 1 条边在 S2 至少对应 **1** 个接口 ⇒ S2 接口规模 ≥ **19**，且可能为数倍。方法草案未定义"1 边→N 接口"的划分规则，也未指定粒度原则归属，S2 极易自定一套与 #5 边粒度脱节的口径。

### C-10a（轮 10）· #5 未把 B/C 层清单交付 #6，两边会各走各的
- **证据原文**（被审方法草案）："B 层·事件通道（发布/订阅，不进 DAG）""C 层·时序（启动顺序·线程归属，不画成图）→ 归 #6/#7"。即 B/C 被"移出"，但**没有"移出后作为单列清单交给 #6"的交代**。
- **证据原文**（`20-设计/S1-架构基线草稿.md` §17.2 决策 17）："**走 `infra/eventbus` 事件通道（`core` 绝不依赖 `app`）**"——这是 #6 画运行时消息流时必须遵守的拓扑；若 #6 不知 #5 已有此约束而自行抽事件流，可能画出 `core→app` 直连，与禁边 `core→app` 冲突。
- **实测数据**：§17.5 数据流中经 `infra/eventbus` 的跳 = **3**（即 B 层清单规模至少 3 条事件路径）；线程归属依据决策 9"每设备一线程 + SPSC 无锁汇聚"覆盖全部 **24** 模块。两边（#5 与 #6）若各自独立对 #17 的 6~8 个场景走查，理论漂移点 = 场景数 ×（事件路径 + 线程路径）≈ **(6~8) × (3 + 1)** 区间。

### C-11a（轮 11）· 边表无拥有者/维护/变更通知，会腐化
- **证据原文**（被审方法草案）："完成判据：① 脚本退出码 0 ② 每条边有「出处」字段 ③ 双向核对无缺口 ④ 独立核验无新增 D"——四条全是**创建期快照判据**，无一条涉及"冻结后谁来改、何时改、改了通知谁"。
- **证据原文**（`../new project/docs/REVIEW-LOG.md`，根因①多次实证）："**① 改完不同步引用点**…… 连'根因的计数本身'都会不同步"；"**凡'计数/枚举/清单'这类元信息，修改后必须单独回看一遍**"。
- **实测数据**：边表下游消费者 = **4** 个（#18、S2、#6、#5 自身脚本）。每发生一次 S2 接口新增 / S4 模块拆分，这 **4** 处都需同步；方法草案当前对这 **4** 处**零**同步机制定义，正是 REVIEW-LOG 根因①在新产物上的发作点。

### C-12a（轮 12）· `check-deps.py` 只校验表内自洽，不校验表 vs 源码（最接近"伪判据"的缺口）
- **证据原文**（被审方法草案）："产出 5 步：边表 → `check-deps.py`（验无环 + 验禁边）→ 双向核对 → 渲染分组图 → 独立核验"；完成判据"① 脚本退出码 0"。**5 步与 4 判据中，没有任何一步提及扫描实际源码（`#include`/调用）**。
- **证据原文**（`../new project/docs/REVIEW-LOG.md`，根因③）："**自评的覆盖性声明不可信**——自己数自己列的东西，必然数漏自己没想到的那个"；"这类'逐项覆盖'结论只能由外部逐项对照得出"。
- **实测数据**：对方法草案文本检索关键词 {源码, `#include`, include, 调用图, 实际代码, 扫描} —— **命中数 = 0**。即方法草案定义的验证**完全自指（表查表）**，可对"码已违反禁边"仍判绿灯。这是可观察失效征兆的源头：脚本长期退出码 0，但 `#18`/`S2`/`#6` 实际依赖与表脱节。

### C-13a（轮 13）· 渲染分组图缺分组维度/密度阈值/短标签规则
- **证据原文**（被审方法草案）："④ 渲染分组图"——只有四字，无分组维度、无阈值、无标签规范。

- **实测数据**：模块 **24** 个；预期唯一边 ≈ **19** 条（§五 14 ∪ §17.5 A 层 8，扣 ≈3 重叠）；边:节点 ≈ **0.8**，单图可读。故本缺口确凿但非致命：缺的是"何时拆层内子图"的阈值与"长路径标签缩写"规则，而非规模本身爆掉。

### C-14a（轮 14）· 边表只记方向，未标语义类型与强度
- **证据原文**（`20-设计/S1-架构基线草稿.md` §五）：每行已区分"**唯一持有者** / **可写者** / **只读者**"；§17.5 数据流含"投递 / 汇聚 / 落成"等语义动词。

## 收敛小结

- **七轮各一个全新角度，共得 7 条确凿 C 类缺口（C-8a ~ C-14a），零纯重复 17 条已知项**；轮 13 偏薄（仅 1 条 C + 若干 I），已如实说明。

- **最重的三条**：① C-12a（验证只查表不查码，完成判据可能伪绿，borderline D）；② C-8a（#5 与 #18 无交接，#18 拿不到编译期依赖图）；③ C-10a（#5 与 #6 各自重造事件/线程拓扑会漂移）。三者都指向同一本质：**方法草案把"创建期"做满了，却没定义"与下游(#18/S2/#6)的交接"和"冻结后的维护"**。

## 明确回答：这套方法现在能不能开始用？

**可以有条件地开始用，但必须先把 7 条 C 中的「交接类」(C-8a/C-9a/C-10a) 与「验证类」(C-12a) 落进方法草案，再动手产出 #5 边表。**

理由：
1. 方法草案的**核心骨架（四层划分、§五+§17.5 抽边、禁边、双向核对、脚本无环校验）是成立的**，前三轮已修掉 17 条硬伤，本轮未发现能推翻骨架的新问题。
2. 但本轮发现的 7 条都是「**边表造出来之后怎么被下游消费、怎么不腐化、怎么真验证**」——若不先补 C-8a/C-9a/C-10a/C-12a，#5 产出的边表会被 #18/S2/#6 各用各的、且可能在代码演进中静默失真，正好重演 REVIEW-LOG 根因①/③。
3. 建议的最小前置动作（不替用户拍板，仅列）：在方法草案补「#5→#18 交接声明」「边→接口规则+粒度归 S2」「B/C 层单列清单交 #6」「源码交叉校验步骤」「边表生命周期」五句话，即可开工；其余（分组渲染阈值、边表语义/强度列）可并行补或后置。
