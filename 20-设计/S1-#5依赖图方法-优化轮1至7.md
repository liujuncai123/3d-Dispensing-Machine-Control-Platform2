## 表二 · 新增 D/C 清单（逐条证据原文 + 实测数据）

> 归类说明：D=违反已冻结条目（阻塞）；C=冻结外新要求；I=可接受可更好；Q=信息不足。
> 本批**新增 D = 0**（R1-N1 因 S1 未冻结暂列 C，S1 冻结后升级为 D，见下）；**C = 11；I = 3**。

### R1-N1（C，S1 冻结后转 D）· 方法漏掉 #5 DoD 的"接口清单"半壁

- **证据原文（被审文件 `20-设计/S1-架构基线草稿.md` §一 任务表 #5）**：
  > "构建块视图 | 依赖图（脚本验「无环」）+ 每模块**接口清单（输入 / 输出 / 错误）** | 🔴 只有模块"
- **方法草案产出 5 步**（边表 → check-deps.py → 双向核对 → 渲染分组图 → 独立核验）**只字未提接口清单**；方法也自称是"#5 构建块视图（依赖图 + 接口）"的方法，正文却只谈依赖图。
- **反证法论证**：若这套方法不存在，作者仍会被 §一 #5 的 DoD 提醒"要做接口清单"；方法反而把它吃掉 → 这一半是方法的减分项。
- **实测**：§一 #5 明确要求"两件套"，方法 5 步中 0 步产出接口清单。
- **是否已知重复**：否（17 条全在 DAG/边 mechanics，无人提接口清单缺失）。
- **处置**：S1 当前未冻结，按 `03-发现分类与变更控制.md` 定义属 C（冻结外新要求）；**一旦 S1 冻结即转为 D（阻塞 #5 交付）**。

### R2-N1（C）· "独立核验无新增 D" 对单人开发不可执行

- **证据原文（方法草案 完成判据④）**："④ 独立核验无新增 D"。
- **项目现实（任务背景）**：单人开发，同一人写方法又自验；REVIEW-LOG 根因③明确："自评的覆盖性声明不可信"。
- **是否已知重复**：是——O7（完成判据不可判定）的同根因投影；O7 修复只加"脚本退出码/出处/双向核对"，未触及"独立核验"在单人项目下无主体。
- **处置**：把"独立核验"替换为项目既有闸门——跑 `check-consistency.py` + 用母清单角度3（覆盖度）/角度4（依赖完整性）逐条勾，而非要求一个不存在的独立人。

### R2-N2（I）· 产出偏重，渲染图可折叠

- **实测清点方法产物**：边表(1) + 模块表 24 行(1) + 禁边清单 4 条(1) + check-deps.py(1) + 双向核对 6~8 场景×2 方向(1) + 渲染分组图(1) + 独立核验(1) = **7 类产物 / 5 步**。
- **证据**：方法"产出 5 步：边表 → check-deps.py（验无环 + 验禁边）→ 双向核对 → 渲染分组图 → 独立核验"。
- **是否已知重复**：否。
- **处置**："渲染分组图"改为"由边表脚本生成的文档内 Mermaid/ASCII 图"，不必独立管线（与 R4-N1 配合）。

### R3-N1（C）· 方向判据只覆盖数据边

- **证据原文（方法草案）**："⚠️ 机械抽的只是『候选』，方向由人工定（判据 = 谁持有 / 谁是写者）"。
- **事实**：§五 数据所有权表只有 11 个数据类的"持有/写者"；而大量"调用/使用型"边（如 `app/dialogs` 用 `core/device`、`core/device` 用 `core/concurrency`）在 §五 中无"持有/写者" → 判据不适用，执行人无法据此定方向。
- **是否已知重复**：否（O4 是"候选边靠人想"，本问题是"方向判定缺判据"，不同）。
- **处置**：区分两类边——数据边用"持有/写者"；调用/使用边用"客户(调用方)→ 服务(被调用方)"。

### R3-N2（I）· 候选源② §17.5 数据流与层规则张力

- **证据原文（方法草案）**："② §17.5 数据流 —— 人工推"；层 B："B 层 · 事件通道 —— 发布 / 订阅（不进 DAG）"；层 D："D 层 · 协议契约 —— 跨进程边界（apps/virtual-device ↔ comm/interface）…（不进 DAG 但单列）"。
- **事实（文件 `S1-架构基线草稿.md` §十七 17.5 数据流）**：该数据流含 "→ infra/eventbus → app/scene3d" 与 "E2 虚拟下位机" 跳——前者属层 B（事件通道，不进 DAG），后者属层 D（跨进程，不进 DAG）。
- **实测**：§17.5 数据流框内包含 `infra/eventbus`（=True）与 `E2`（=True）；把运行时流推进 DAG 候选会产出被层规则剔除的边。
- **是否已知重复**：否（F1 是"§四 抽候选 0 命中"，本问题是"§17.5 与层规则冲突"）。
- **处置**：来源②明确"只取落在上位机四层内的静态使用关系"，或在抽取时打 `runtime-excluded` 标记。

### R4-N1（C）· 渲染分组图与 C3 冲突风险

- **证据原文（方法草案 步骤4）**："渲染分组图" 并列于 "边表列（机器可读，**唯一权威源**）"。
- **文件 `00-流程/02-文件结构规范.md` C3**："同类信息**只有一个权威源**，别处只引用不复制"。
- **事实**：若"渲染分组图"手画独立产出，则出现"边表一份图 + 手画一份图"两份图 ⇒ 违反 C3。方法未声明该图"由边表派生"。
- **是否已知重复**：否（C3 是既有机制，但这是新应用点）。
- **处置**：明文写"渲染图必须由边表脚本生成 / 由边表导出，不得另存一份"。

### R4-N2（C）· 禁边清单双载体 ⇒ C9 / 根因① 风险

- **证据原文（方法草案）**："禁边清单（不产生边，只产生禁止项）：core → app · comm → 业务 · infra → 业务 · apps/virtual-device → 任何上位机模块" + "check-deps.py（验…**验禁边**）"。
- **文件 `02-文件结构规范.md` C9**："改完一处内容后，必须回搜『哪些地方引用了它』并逐处同步"；REVIEW-LOG 根因①："改完不同步引用点"。
- **事实**：禁边既写在方法文字里，又硬编码进脚本；改一处漏另一处 ⇒ 经典"改完不同步"。
- **是否已知重复**：是（根因① 改完不同步投影）。
- **处置**：禁边只在**一处**（边表文件内 `[forbidden]` 段），脚本读它，不硬编码。

### R4-N3（C）· 方法完成判据与机制4 收敛判据平行重叠

- **证据原文（文件 `00-流程/01-开发流程.md` 机制4）**："同层把母清单 8 个角度逐项跑完，且新增 D 类 = 0 ⇒ 该层可冻结"。
- **方法草案 完成判据**：另立 4 条（脚本退出码0 / 每条边有出处 / 双向核对无缺口 / 独立核验无新增 D）。
- **事实**：#5 是 S1 子任务，本应纳入机制4；方法另立一套完成判据 ⇒ 两套判据可能打架。
- **是否已知重复**：是（O7 投影）。
- **处置**：声明"方法完成判据 = 机制4 母清单 在 #5 上的实例化（角度4 依赖完整性 + 角度3 覆盖度）"，而非平行物。

### R5-N1（C，未决）· 边表行格式未钉死

- **证据原文（方法草案）**："边表列（机器可读，唯一权威源）：使用者 → 被使用者 : 出处（可 grep）"——只给了**列含义**，没给**每行怎么写**。
- **事实**：check-deps.py 要解析边表，但行格式（分隔符、注释约定、方向箭头）未定 ⇒ 换人无法起步，且"可 grep"不等于"可解析"。
- **是否已知重复**：否（O5/F3 谈的是列/位置，不是行序列化格式）。
- **处置**：钉死行格式，例：`使用者 -> 被使用者 [layer=A] : 出处`，并附 2~3 行示例；脚本按此解析。

### R5-N2（C）· 出处字段未遵守 C2

- **证据原文（文件 `02-文件结构规范.md` C2）**："锚点用『节标题 + 被引原文短语』，**禁止行号引用**（改一行即失效且无声）"。
- **方法草案**："出处（可 grep）"未约束形态 ⇒ 执行人极易写"§五 第3行"类行号引用，违反 C2。
- **是否已知重复**：否。
- **处置**：出处强制 C2 形态：`<相对路径>::<节标题>::<被引短语>`。

### R6-N1（I）· 脚本能力边界未用足

- **证据原文（方法草案）**："check-deps.py（验无环 + 验禁边）"；完成判据②："每条边有『出处』字段"。
- **事实**：脚本本可机械验两项却没验——① 每条边两端都是 **模块表（24 行，S1 §十六 权威数）** 中的合法模块（参照完整性 = 母清单角度4）；② 每条边 出处 非空且合规。使判据②沦为人工自评 ⇒ 根因③。
- **实测**：方法禁边 4 条、模块表 24 行；脚本若只验 2 项则漏验这 2 项。
- **是否已知重复**：部分（根因③ / O7 投影），但角度是"脚本能力边界"。
- **处置**：脚本加两条断言——端点 ∈ 模块表；出处非空且符合 C2。

### R6-N2（C）· "漏边"不可机械证 + 自评覆盖不可信

- **证据原文（方法草案）**："正向：场景走的每一跳，图上必须有边（查漏）"；完成判据③："双向核对无缺口"。
- **事实**：① "漏边"根本不能机械证（无法证明没漏掉从没想过的依赖）；② 正向核对把运行时场景跳（含 eventbus/E2）映射成静态边，必现假缺口或误植（与 R7-N1 同源）；③ "无缺口"是人自评覆盖，正是 REVIEW-LOG 根因③ 警告的不可信声明。
- **是否已知重复**：是（根因③ / P4 验不了漏边 投影）。
- **处置**：承认"漏边不可机械证"；正向核对限定为"§五 11 个数据类的持有者都作为节点出现在图中"（可机械验）；运行时跳单独在 #17 核；删除"无缺口"绝对自陈，改为"已核对 X 场景，缺口清单如下"。

### R7-N1（C）· 双向核对正向 静态/运行时 类型错配

- **证据原文（方法草案）**："正向：场景走的每一跳，图上必须有边"。
- **文件 `S1-架构基线草稿.md` §十七 17.5**：#17 场景含 "→ infra/eventbus"（层 B，不进 DAG）与 "E2 虚拟下位机"（层 D，不进 DAG）。
- **事实**：把 #17 运行时跳硬映射成静态 DAG 边，会制造假缺口或把禁边/非 DAG 边塞进图。
- **是否已知重复**：否（F4 是"对象太少变假核对"，本角度是"对象类型错配"）。
- **处置**：#5 只核"静态使用边"；运行时/事件/跨进程跳交给 #17。

### R7-N2（C）· #17 与 #5 共享底物，边界未定

- **证据原文（方法草案）**："拿 6~8 个关键场景（#17 的清单）双向核对"——暗示 #5 用 #17 清单，但没说 #17 反过来以 #5 边表为输入。
- **文件 `02-文件结构规范.md` C3**：单一权威源。
- **事实**：两任务共享"模块依赖"底物；若各自生成一份图 ⇒ 两份图 = 违反 C3（与 R4-N1 同源）。
- **是否已知重复**：否（与 R4-N1 同源 C3，但 R4-N1 本身非 17 条）。
- **处置**：在 #5 定稿写明"#17 走查以本边表为输入；#5 不重复 #17 的运行时/机制走查"。
