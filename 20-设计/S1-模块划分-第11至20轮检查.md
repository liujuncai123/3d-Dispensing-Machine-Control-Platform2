## 轮 11 · 数据流闭环（关键数据从产生到消费跨几个模块）

**查法**：追"坐标"这条数据的全链路。

| 环节 | 模块 |
|---|---|
| 产生 | 独立单元（虚拟下位机） |
| 接收 | `comm/interface` → `comm/modbus` |
| 汇聚 | `core/concurrency` |
| 存 | `core/device` |
| **坐标 → 几何位置变换** | **`app/scene3d`**（上轮决定） |
| 画 | `app/scene3d` |

### 🔴 发现 11：**坐标映射放 UI 层是错的**

"坐标 → 几何变换"是**纯计算**（业务逻辑），把它放 `app/scene3d` ⇒ **UI 层含业务逻辑** ⇒ 违反四层的依赖方向（UI 只该做表现）。

⇒ **应回业务层**。

---

## 轮 12 · 状态归属（存在哪、谁写谁读）

**查法**：对 `REQ-DEV-003`（单一事实源）+ `B-017b`（每设备一线程 + SPSC）问三个问题。

| 问题 | 答案 | 判定 |
|---|---|---|
| 状态**存在哪** | `core/device` | ✅ |
| 状态**谁写** | `core/concurrency` 的设备线程 | ⚠️ **写者与持有者分离** |
| 状态**谁读** | UI 各视图 / `core/stats` / `core/alarm` | ✅ |

### ⚠️ 发现 12：写者（concurrency）与持有者（device）分离有风险

若不写死"**状态只有一个持有者**"，会出现两处状态 ⇒ 回到老问题。
⇒ **必须在 A4 接口设计里定死**：`core/device` 是唯一持有者，`core/concurrency` 只"投递"不"持有"。

---

## 轮 13 · 错误 / 异常传播路径

**查法**：挑 3 个异常，看它怎么从底层传到界面。

| 异常 | 传播路径 | 判定 |
|---|---|---|
| 通信掉线 | `comm` → **？** → `core/execution`（停机）+ `app/dashboard`（提示） | 🔴 **中间那段没有归属** |
| 误差超阈值 | `core/error` → `core/alarm` → `data/log` + UI | ⚠️ 靠直连 |
| 归正下发失败 | `comm` → `core/error` → UI | 🔴 同上 |

### 🔴 发现 13（**重要**）：**缺"事件/信号传播机制"的归属模块**

**没有任何模块负责**"底层发生的事怎么通知上层"。若靠"谁需要谁直连"，会造成 **core → app 的反向依赖**（轮 2 已预警过，这里是它的落地缺口）。

⇒ **必须有一个事件通道**（Qt 信号槽的集中封装，或事件总线）。

## 轮 15 · 配置归属

**查法**：`REQ-INF-006`（参数可配置）说"配置集中管理"，那**集中在哪个模块**？

| 配置项 | 现在会落在哪 |
|---|---|
| 刷新率（50ms/100ms） | `app/scene3d` ? |
| 掉线阈值（3s） | `core/device` ? |
| 误差超阈值 | `core/alarm` ? |
| 台数上限（8） | `core/device` ? |
| 日志保留量 | `data/log` ? |

### 🔴 发现 15：缺"配置管理"归属

`REQ-INF-006` 判据②要求"配置**集中管理**（一处定义）"，但模块划分里**没有"配置"这个家**。
⇒ 若散在各模块，就**直接违反 `REQ-INF-006`**。

## 轮 16 · 线程边界

**查法**：哪些模块跨线程、哪些必须主线程。

| 模块 | 线程 | 判定 |
|---|---|---|
| `core/concurrency` | 多线程（每设备一线程） | ✅ |
| `core/device` | 被多线程写 | ⚠️ 需同步保护 |
| **`app/*`** | **必须主线程** | ⚠️ 需写明"UI 不得被工作线程直接调" |
| `core/statemachine` | ？ | ⚠️ **没定**（状态机在哪个线程跑？） |

### ⚠️ 发现 16：缺"模块 × 线程"约束表

尤其：**状态机跑在哪个线程**没定 ⇒ 这会直接影响 `B-017b` 的实现。

## 轮 17 · 性能热点路径

**查法**：`REQ-NFR-008`（数据 50ms / UI 100ms）这条路径跨几个模块。

```
comm(收) → core/concurrency(汇聚) → core/device(存) → core/mapping(变换) → app/scene3d(画)
```

⇒ **跨 5 个模块**。

### ⚠️ 发现 17：这条路径上**任何一层阻塞都会拖垮刷新率**

⇒ 需在接口设计里明确："**这条路径上不得有磁盘 IO / 锁等待 / 长计算**"。

---

## 轮 18 · 命名一致性

**查法**：模块名是否符合 `B-025`（按层 + 层内按模块）的规范。

| 模块 | 前缀 | 判定 |
|---|---|---|
| `app/*` `core/*` `comm/*` `data/*` `infra` | ✅ 按层 | ✅ |
| **`virtual-device`**（独立单元） | ❌ **无前缀** | ⚠️ 不一致 |

### ⚠️ 发现 18：独立单元命名不成体系

⇒ 建议改为 `apps/virtual-device`（与上位机的 `app/` 形成体系）。

## ⚠️ 本轮最重要的一条教训

> **"10 轮无新根因" ≠ "10 轮后仍无新根因"。**
> 我上轮说"第 10 轮无新根因 ⇒ 已收敛" —— **逻辑错误**：那只是"一轮内无新根因"。
> 正确判据（项目已定）：**"同一层面连续 10+ 轮 0 新根因"** 才收敛。
> ⇒ 本轮（11~20）**连续又出 5 个新根因** ⇒ **远未收敛**。
