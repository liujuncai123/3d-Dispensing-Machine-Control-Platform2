## 表二 · 新增 D 类清单（逐条给证据原文）

### D-1 · §十七 决策5⑤ 与 §十二 A4 自相矛盾（文档自相矛盾）

- **证据 1**（`20-设计/S1-架构基线草稿.md` · §十七 §17.2 决策表第 5 行）：
  > 「**上下解耦靠事件** | `core` **绝不依赖 `app`**；底层有事往上通知走 `infra/eventbus`」
- **证据 2**（同文件 · §十二 关注点总表 A 类）：
  > 「A4 | **事件 / 消息**（模块间通知） | **待设计** —— 底层事件如何通知上层（★轮13 查出"缺事件通道归属"） | 🔴 **待设计**」
- **判定**：同一份 S1 文档内，决策清单称「事件机制已决（走 `infra/eventbus`）」，关注点表称「仍待设计（缺事件通道归属）」。两说互斥 → 文档自相矛盾（违反 `03-发现分类与变更控制.md` 的 D 类定义「文档自相矛盾」）。
- **后果**：决策 9（每设备一线程 + SPSC 汇聚）的「汇聚后如何通知 UI」、决策 11（急停）的「本地优先如何落到通道」都依赖此机制，但机制本身状态不明，导致决策不可落地、不可验证（与轮 17/19 互相印证）。

### D-2 · 9 项预留中 5 项在 §17.2 无任何承载决策，违反 S-1 §四 冻结承诺

- **证据 1**（`10-基线/S-1-立项声明.md` · §四 预留清单）：
  > 「⏳ 预留（有接口、无实现，**9 项**） | ① 物理仿真 ② 预测性维护 ③ 真实 CCD 视觉 ④ PID / 自适应补偿 ⑤ DXF / G 代码 / PLT 导入 ⑥ OPC UA / SECS/GEM ⑦ 配方库 / 版本 / 审计 ⑧ MES / ERP 对接 ⑨ **Linux / macOS 多平台构建与安装包**」
- **证据 2**（同文件 · §四 预留定义）：
  > 「多平台「预留」的落地定义：代码**不写平台相关**（不硬编码 Windows 路径 / 不用 Win32 API / 不让 `#ifdef` 塞业务逻辑）；但**不做**目标平台构建。」
  > （同节总定义）「预留 = 有接口、无实现」
- **证据 3**（`20-设计/S1-架构基线草稿.md` · §17.2 决策表 15 条 + §六 6.3 ARCH 8 项）：
  > 15 条决策中 **无一条**显式承载 ①物理仿真 / ②预测性维护 / ④PID / ⑤DXF导入 / ⑦配方库；§六 6.3 的 `REQ-ARCH-001~008` = 「趋势曲线 / 故障注入 / 报警洪泛 / 传感器仿真 / 基元扩展 / 开机自检 / 中断恢复 / 时间预估」，亦**不含**此 5 项。
- **判定**：S-1 §四 已冻结承诺「预留 = 有接口、无实现」；但其中 **5 项（① ② ④ ⑤ ⑦）在 §17.2、§六 ARCH、S0 REQ-ARCH-001~008 三处均无任何接口点** → 冻结承诺的「有接口」前提在架构层落空 → 违反已冻结条目（D 类）。
- **后果**：直接回答用户「15 个够吗」—— 不够。预留项的「承载」在决策清单里是真空的。这 5 项若真做完接口预留，势必要新增 §17.2 决策（见 表三 C1）。

### D-3 · §17.2 标「全部已裁」与同文件「未冻结 / 待裁」状态自相矛盾

- **证据 1**（`20-设计/S1-架构基线草稿.md` · 文件页眉）：
  > 「**状态**：🔄 起草中（**未冻结**）」
- **证据 2**（同文件 · §十七 开头）：
  > 「### 17.2 根本性决策清单（**15 条 · 全部已裁**）」
- **证据 3**（同文件 · §十七 §17.1 / #12 标题）：
  > 「### 17.1 一句话架构策略」（无「已裁」标）+ 「#12 解决方案策略（🟡 **草案 · 待裁**）」
- **判定**：同一文档内，§17.2 自称「15 条·全部已裁」，而文件页眉为「未冻结」、§十七 整体为「草案·待裁」。若已「全部已裁」，则不应仍处「未冻结/待裁」。状态标注与内容自相矛盾（D 类「文档自相矛盾」）。且与项目事实一致——用户仅确认过 §17.1（见任务背景），§17.2 尚未裁决。
- **后果**：「全部已裁」的标注虚假，使读者误以为这 15 条已锁死；实际它们仍在待裁态，且与 §十二 仍标「待设计」的 A4/A9/A10/A11 等机制存在依赖（见轮 16/19），构成「已裁」与「依赖待设计」的内在冲突。
