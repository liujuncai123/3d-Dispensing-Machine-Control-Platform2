## 表二 · 新增 D / C / I 清单（逐条给证据原文）

> 归类说明：**D=阻塞（本批 0 条）**；**C=成本/建议**；**I=信息/一致性缺口**。本批无 D，因 `check-deps.py` 退出码 0 已证图内部自洽（无环/无禁边/端点合法/出处无行号）。

### NEW-1（轮 1 · I · 全新根因）进程边界节点「同物异名」

- **结论**：D 层协议边把虚拟下位机写作模块名 `apps/virtual-device`，而上下文视图把同一事物称作外部实体 `E2`；#18 做 2-target 切分时需在两套名字间人工映射，边表与上下文视图对「系统外」的命名不统一。
- **证据（被检对象原文）**：
  - `20-设计/S1-依赖边表.txt`：`comm/interface -> apps/virtual-device | D | protocol | §14.2 E2(Modbus TCP 语义,下发)` 与 `apps/virtual-device -> comm/interface | D | protocol | §14.2 E2(上报坐标/状态/误差/IO)`。
  - `20-设计/S1-架构基线草稿.md`（§14.2 外部实体清单）：「**E2** | **虚拟下位机**（`apps/virtual-device`·**独立进程**·**与上位机同机回环**·**多实例 ×N，N ≤ 8**）」。
  - `00-流程/check-deps.py`：`MODULES = { … 'apps/virtual-device'}` 且 `EXTERNAL = {'E1','E2', …,'qt','vtk','main'}`——`apps/virtual-device` 在 MODULES 不在 EXTERNAL，而 `E2` 在 EXTERNAL 不在 MODULES，二者从不互指。
- **是否已知重复**：否（新根因，非已知 40+ 中任一项）。

### NEW-2（轮 2 · C · 全新根因）增量编译影响面失控（高扇入核心）

- **结论**：改 `data/log` 头会触发 **13** 个模块重编、改 `core/device`/`core/statemachine`/`data/store`/`core/concurrency` 头各触发 **11** 个模块重编；且牵连集里都含 `app/scene3d`——它是 24 模块里**唯一**吃 VTK+Qt 头的重 TU，单次重编可能 1–3 分钟。这是确定的构建瓶颈，应优先对高扇入核心模块做 PIMPL / 不透明指针，把值类型下沉到 .cpp。
- **证据（实测）**：临时分析脚本对 A 层 59 边做反向可达（改 X.h 触发重编的模块集，含自身）：`data/log=13`、`core/device=11`、`core/statemachine=11`、`data/store=11`、`core/concurrency=11`、`core/program=7`；且 `app/scene3d` 出现在上述每一集里。
- **证据（边表原文，高扇入示例）**：
  - `20-设计/S1-依赖边表.txt`：`app/scene3d -> core/device | A | usage`、`app/scene3d -> core/mapping | A | usage`、`app/scene3d -> core/program | A | usage`、`app/scene3d -> vtk | A | usage`、`app/scene3d -> qt | A | usage`（scene3d 同时依赖多个高扇入 core 模块与 VTK/Qt）。
  - `core/execution -> data/log | A | usage`、`core/device -> data/log | A | usage`、`core/error -> data/log | A | usage`、`core/alarm -> data/log | A | usage`、`core/program -> data/log | A | usage`、`core/statemachine -> data/log | A | usage`、`app/dashboard -> data/log | A | usage`、`app/dialogs -> data/log | A | usage`（data/log 被 10 个模块直接依赖）。
- **是否已知重复**：否（前批无任何「增量编译 / 扇入」角度）。

### NEW-3（轮 3 · I · 同根因投影：loop-2「脚本 3 缺口」）「core 不暴露 Qt/VTK 头」在 S1 不可证

- **结论**：方法 §三 禁边写「`core/* → qt` / `core/* → vtk` / `comm/* → vtk` / `data/* → vtk`」，但 `check-deps.py` 的 `forbidden()` 仅对 **A 层**检查此禁边；它只验证「模块级」无 `core/comm/data -> qt/vtk` 边，无法验证「core 头文件是否 `#include <QVector3D>` / `<vtkXxx>` 这类 Qt/VTK 类型」。即「core 不暴露 Qt/VTK 头」这条铁律在 S1 阶段**不能由边表或脚本证明**，且方法 §十 完成判据 6 条未包含此项。
- **证据（被检对象原文）**：
  - `20-设计/S1-#5依赖图方法-定稿.md`（§三 禁边）：「`core/* → qt` / `core/* → vtk` / `comm/* → vtk` / `data/* → vtk` | "核心不暴露 Qt/VTK 头"（模块划分轮 32）」。
  - `00-流程/check-deps.py`：`def forbidden(a, b, layer): … if layer != 'A': return None   # ↓ 以下仅 A 层（静态依赖）适用` 之后才有 `if a.startswith(('core/','comm/','data/')) and b in ('qt','vtk'): return '核心/通信/数据 → 第三方库…'`。
  - `20-设计/S1-#5依赖图方法-定稿.md`（§一）：「编译期依赖 = 使用期依赖 + 头文件暴露策略，是 `#18 构建组织` 的产物，不是输入」。→ 暴露策略本就归 #18/S4，故 S1 边表查不到。
- **是否已知重复**：与 loop-2「脚本 3 缺口（脚本对源码零命中）」**同根因投影**（脚本查不全）；但「头文件暴露」这一具体验证点前批未点名，本批补实。

### NEW-4（轮 4 · C · 全新根因）跨进程协议无共享模块承载（链接组织缺口）

- **结论**：D 层 `comm/interface <-> apps/virtual-device` 是跨进程协议契约，其「线格式 / 结构体定义」在边表里**没有归属模块**——上位机侧与下位机侧必须就字节布局达成一致，却没有一个被两边共同链接的 shared 模块承载。#18 决定链接时，无法从边表推出「是否要建一个 protocol lib 被两个 target 共同链接」，只能实现期各写各的，存在漂移风险。
- **证据（被检对象原文）**：
  - `20-设计/S1-依赖边表.txt`：`comm/interface -> apps/virtual-device | D | protocol`、`apps/virtual-device -> comm/interface | D | protocol`（仅此两条；无任何模块同时服务两侧）。
  - `20-设计/S1-架构基线草稿.md`（§十二 B3 序列化/数据格式）：「**待设计** —— 通信帧格式？程序文件格式？日志格式？」。
  - `20-设计/S1-架构基线草稿.md`（§14.5 外部实体硬约束 1）：「E2 是独立进程 ⇒ 上位机与它之间**只能靠超时/心跳判定存活**，**不能靠"函数返回"**」→ 两侧不是同一二进制，更凸显需共享线格式定义。
- **一致项（非发现）**：`apps/virtual-device` 在边表中除 D 边外对上位机零 A 边，几乎自包含，可独立成最小 target，与「独立进程」一致。
- **是否已知重复**：否（新根因）。

### NEW-5（轮 6 · I · 全新根因）`#5 → #18` 交接是「半截」（必要非充分）

- **结论**：方法 §一/§八 把「编译期图」说成可由 `#5` 直接支撑（交使用期边表，`#18` 据此+暴露策略推），但暴露策略在 S4 写码时才定、S1 不存在；同时基线 §1.0.2 把「构建组织（CMake target 怎么划）」列为**待做项 #18**。二者矛盾：方法高估了边表对 #18 的支撑度——边表是 `#18` 的必要非充分条件，S1 阶段 `#18` 推不出编译期图。
- **证据（被检对象原文）**：
  - `20-设计/S1-#5依赖图方法-定稿.md`（§一）：「`#5` → `#18` 必须交接：`#5` 交"使用期边表"，`#18` 据此 + 暴露策略 推出编译期图」。
  - `20-设计/S1-#5依赖图方法-定稿.md`（§八）：「`#5` → `#18` 交接声明：`#5` 交"A 层使用期边表 + 接口清单"；`#18` 据此 + 头文件暴露策略 推编译期图与 CMake target」。
  - `20-设计/S1-架构基线草稿.md`（§1.0.2）：「**18** 🆕 | **构建组织**（CMake target 怎么划） | C4 Container 层 | 全部模块 ⇒ **是每个模块一个 CMake target，还是 1 个？**…缺它 ⇒ 编译依赖关系没法管、**增量编译策略定不了**」→ #18 本身仍「待做」。
- **是否已知重复**：否（新根因）。

### NEW-6（轮 9 · C · 全新根因）构建时间预算缺 binary cache / ccache

- **结论**：VTK 是巨型库，vcpkg 源码构建首建量级可能 30–60+ 分钟；运行期仅 `app/scene3d` 一个 TU 吃 VTK 头（实测全表唯一 `-> vtk` 节点）。方法/基线只提「vcpkg + CMake」「主程序走 MSVC」「构建前清代理变量」，未提 vcpkg binary caching / ccache。对「单人 + 秋招档期」，每次 clean build VTK 不现实，必须靠缓存把全量压成增量；增量本身可行（改 core 头触发 scene3d 重编约 1–3 分钟），但高频改高扇入核心时累积明显。
- **证据（被检对象原文）**：
  - `20-设计/S1-架构基线草稿.md`（§17.2 决策 15）：「构建 | **vcpkg + CMake**，产出 **2 个可执行 target**…**① 主程序走 MSVC**（VTK 是 MSVC 编的）**② CMake 须显式指定 `Qt6_DIR`** **③ 构建前须清代理变量**」。
  - `20-设计/S1-依赖边表.txt`：`app/scene3d -> vtk | A | usage`（唯一 VTK 消费点）。
  - `20-设计/S1-架构基线草稿.md`（§十二 C2）：「构建与部署 | vcpkg + CMake，**2 个可执行 target**」——未提缓存。
  - `REQ-INF-001`（基线 §四 映射表）：「一键构建」——无缓存则「一键」首建仍极慢。
- **是否已知重复**：否（前批未做工程量级 / 缓存评估）。

## 表三 · 测试替身清单（轮 8 产出，逐条边）

> **判定规则（依据）**：
> - 被测模块 = 核心模块（`core/*` + `comm/interface`，依 `REQ-INF-002`「核心模块有单元测试」）时，其依赖按「构造注入 / 可 mock」原则处理。
> - `infra/*`（config/eventbus/lifecycle）：**mock**——构造注入假实现（`§7.2` / 约束 2「禁单例」）。
> - `comm/interface`：**mock**——`REQ-COM-001` 判据③「业务不依赖具体协议 / 可 mock」。
> - `apps/virtual-device`（跨进程对端）：**mock**——fake device（独立进程，无真链接）。
> - `data/log` / `data/store`：**mock 或 in-memory 真实现**——接口注入（单测用内存版更稳，隔离文件 IO）。
> - 其它 `core/*`（core→core）：**mock**——`core/*` 易变（方法 §四「comm/interface 稳定 · core/* 易变」），单测隔离被测单元。
