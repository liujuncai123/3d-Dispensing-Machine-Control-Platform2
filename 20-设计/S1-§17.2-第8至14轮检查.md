## 表二：新增 D 类清单（逐条证据原文）

> 判定口径：D = 违反已冻结条目，或文档自相矛盾（依 `00-流程/03-发现分类与变更控制.md` §一 + `01-开发流程.md` 机制 4 角度 2「内部一致性」）。本轮新增 D 共 **2 条**；另有 1 条最高风险缺口（D-新-3）当前判 C，若按字面固化配置则升级为 D。

### D-新-1 · 事件总线机制「已定」与「待设计」在同一文档内自相矛盾

- **证据 A（已定）**：`20-设计/S1-架构基线草稿.md` §17.1 五根主干 ⑤："**上下解耦靠事件** | core 绝不依赖 app；底层有事往上通知走 **infra/eventbus**"。
- **证据 B（已定/既存）**：同文件 §八 约束 2："**infra/config · infra/eventbus 必须构造注入**"——把 `infra/eventbus` 当作既存、须注入的组件。
- **证据 C（待设计）**：同文件 §十二 A4："**A4 | 事件 / 消息（模块间通知） | 待设计 —— 底层事件如何通知上层（★轮 13 查出'缺事件通道归属'）**"。
- **矛盾**：同一机制在 §17.1/§八 被当作"已采用的决策/既存组件"，在 §十二 A4 却仍标"待设计、缺归属"。§十二 A4 与 §17.1、§八 冲突，属 **文档自相矛盾**（违反 `01-开发流程.md` 机制 4 角度 2）。另：§17.2「根本性决策清单」15 条中**完全没有**事件总线这一根本决策行，而它恰恰是"core 绝不依赖 app"的落地手段（§17.1 主干⑤），缺它 §17.2 不完整。
- **处置**：将 §十二 A4 改为"✅ 已定：infra/eventbus（依 §17.1 主干⑤、§八 约束 2）"，并在 §17.2 补一条「模块间通知 = infra/eventbus」决策（见 表三 C-1）。

### D-新-2 · §17.2 表头"全部已裁"与项目实际裁决状态冲突

- **证据 A（文档自陈）**：`20-设计/S1-架构基线草稿.md` §17.2 表头："**根本性决策清单（15 条 · 全部已裁）**"。
- **证据 B（流程要求）**：`00-流程/01-开发流程.md` 机制 3 附加前提："**用户原话**：「方案 b 不是选择而是都要进行」—— 即'逐条查看内容'是**必经环节**……**适用哪些层**：S0 起每层都要：S1 逐条看架构决策"。
- **证据 C（实际状态）**：本次任务明确"用户至今只确认过 §17.1。§17.2 任何一条都可能有问题"；且 S1 整体处于"🔄 起草中（未冻结）"状态。
- **矛盾**：表头称"全部已裁"，但 §17.2 尚未经用户内容级逐条查看（机制 3 必经环节未走），与流程要求及实际状态冲突。该标签会使读者误判为"已冻结、可不再议"，违反 `01-开发流程.md` 机制 4 角度 2（内部一致性）。*（若"已裁"仅指"每条均有已裁依据/引用了 B-/A-"，则降为 I；请用户裁定口径。）*

### D-新-3（当前判 C，最高风险；升级条件见下）· #14 构造注入 与 REQ-INF-007 的运行期配置冲突

- **证据 A（决策）**：`20-设计/S1-架构基线草稿.md` §17.2 #14："**配置 | 强类型结构体 + 构造注入；禁单例、禁字符串键**"；同文件 §7.2："**构造注入** | 模块构造时接收自己的结构体，**不读全局**" + "**测试时注入假结构体**"。
- **证据 B（已冻需求）**：`10-基线/S0-需求基线.md` `REQ-INF-007`："**重要设置变更→二次确认（无时间）**"；其验收判据含"**可整体关闭（推荐标准 = 开启，关闭需显式配置）**"与"**本条不得绕过 REQ-RUN-004（急停本地优先）**"——即"重要设置"本身在运行期可经配置改变并生效。
- **冲突**：REQ-INF-007 要求"运行期重要设置变更（二次确认后）生效"，但 #14 + §7.2 描述的机制是"构造时接收结构体、不读全局、测试注入假结构体"，**全文无任何运行期重新加载/通知路径**。若按字面"构造时固化"实现，REQ-INF-007 无法满足 ⇒ 违反已冻结条目。
- **为何当前判 C 而非 D**：#14 未**明示禁止**运行期变更（构造注入亦可注入"可变的配置持有者对象"），属**机制缺口**而非明示矛盾；但这是本轮**最高风险缺口**。
- **升级条件**：若在 S2 前不澄清"运行期变更如何生效"，且实现按"构造时固化"字面落地，则立即升级为 D（违反 REQ-INF-007）。详见 表四 问题①与替代方案。

## 表四：轮 14 配置架构专项（§17.2 第 14 条 / §7.2）

> 用户原话："这一条架构感觉不好"。以下逐条审 §7.2 与 #14。

### 问题清单

**问题① · 构造注入 = 启动固化，与 REQ-INF-007（运行期改配置）冲突？改了怎么生效？**
- `S1-架构基线草稿.md` §7.2："**构造注入 = 模块构造时接收自己的结构体，不读全局**" + "**测试时注入假结构体**"；#14："**强类型结构体 + 构造注入；禁单例、禁字符串键**"。
- `S0-需求基线.md` `REQ-INF-007`："**重要设置变更→二次确认（无时间）**"，验收判据含"可整体关闭（推荐标准=开启，关闭需显式配置）"与"本条不得绕过 REQ-RUN-004"。且 §七 配置项表"哪些设置算'重要'"明确列了**工艺参数/行程/急停/误差阈值**——这些都是运行期会变的重要设置。
- **结论**：#14 + §7.2 描述的机制**没有运行期重新加载/通知路径**。若按"构造时固化"字面实现，REQ-INF-007 无法满足（见 D-新-3）。必须澄清：构造注入的到底是"值"还是"可变的配置持有者对象"；若是后者，需补"运行期经同一持有者更新 + 变更通知"机制。

**问题② · infra/config 组装各模块结构体 ⇒ 是否反向依赖业务模块、成环？**
- `S1-架构基线草稿.md` §7.2："**infra/config 只负责：加载 → 校验 → 组装成各模块的结构体**" + "**不暴露'字符串键'给业务**"。
- 要"组装 `Scene3dConfig` / `DeviceConfig` / …"，`infra/config` 必须 `#include` 或依赖各业务模块（`app/scene3d`、`core/device` …）的**结构体类型** ⇒ `infra → app` / `infra → core` 的依赖方向，与 #4 四层、#8 对下协议、§17.5"infra 贯穿、构造注入禁单例"所隐含的"业务依赖 infra、而非反向"**张力**，存在成环风险。
- **结论**：§7.2 的"组装"措辞与分层依赖方向原则冲突。需在落点层面规定"配置结构体类型定义在哪、infra 如何在不反向依赖业务实现的前提下拿到类型"，否则会在 S2 接口设计时引爆依赖环（见 C-8）。

**问题③ · "禁字符串键"但 JSON 字段名 ↔ 结构体字段名的对应关系谁保证？改名会不会断兼容（对照 REQ-DB-005）？**
- `S1-架构基线草稿.md` §7.2 禁止 1："`Config::instance().get("ui.refresh_ms")`（全局单例 + 字符串键）"——理由是"无类型检查（写错键名编译期不报）"。但持久化是 JSON（#13："SQLite（业务）+ JSON（配置）"），**JSON 本身就用字符串字段名**（`uiRefreshMs` 等）。
- 谁保证"JSON 字段名"与"强类型结构体字段名"一致？若某结构体字段改名，JSON 反序列化（无论用库还是手写映射）须同步改，否则**既有配置文件读不出/读错**。`REQ-DB-005`（数据标准化，统一字段格式）要求字段名一致与可追溯，但配置兼容（改名后旧文件怎么办）无 owner、无迁移策略。
- **结论**：禁字符串键只解决了"运行期取值的类型安全"，没解决"持久化格式 ↔ 结构体"的一致性 ownership 与向后兼容（见 C-7）。

**问题④ · 配置文件组织（一个大文件？分片？）、变更通知、默认值/取值范围校验的落点，有没有定？**
- `S1-架构基线草稿.md` §七 列了 12 类配置项，但**从未说明它们在文件里怎么组织**（一个全局 config.json？按模块分片？默认值内嵌？）。§13 只说"SQLite（业务）+ JSON（配置）"。
- "变更通知"：若运行期改了重要设置（问题①），谁通知订阅方？§7.2 的构造注入模型**没有变更通知机制**（构造后模块各自持有，无观察者）。
- "默认值/取值范围校验"：§7.2 说 infra/config 负责"加载 → 校验"，但**默认值从哪来**（每结构体自带默认？独立 defaults 文件？）、**取值范围在哪校验/由谁校验**，均未定。
- **结论**：配置架构在"组织 / 通知 / 默认值校验"三处落点全空（见 C-7、C-2）。

**问题⑤ · §7.1 不可配置"急停本地优先" 与 §七"重要设置含急停"措辞模糊**
- `S1-架构基线草稿.md` §7.1 不可配置项："**急停本地优先（REQ-RUN-004）** | 安全底线，关掉就出事故" + "以上**只能改实现，不能通过配置关闭**"。
- 同文件 §七 配置项表："**哪些设置算'重要' | core/execution + app/dialogs | 工艺参数/行程/急停/误差阈值**"。
- **模糊点**："重要设置"里的"急停"与 §7.1 不可配置的"急停本地优先"是否同一物？若是，则一处"可经二次确认改"、一处"只能改实现不能配置关闭"，**直接矛盾**；若否（"急停"指急停相关可调参数如减速度/阈值，非本地优先开关），则措辞须显式排除安全开关。`REQ-INF-007` 验收判据已写"本条不得绕过 REQ-RUN-004"，说明二次确认机制本身不得动急停本地优先——§七 那行应据此改写以避免误读。
- **结论**：措辞歧义 → C（需澄清，非硬矛盾）。
