# S1 模块划分 · 10 轮检查报告

> ⚠️ **2026-09-21 更新（`CR-010`）**：模块计数由 **24 改为 25**（新增 `app/replay`，口径不变 = 数全部路径）。本文正文里的旧数（18 / 21 / 22 / 24）**一律作废**，以 `./S1-架构基线草稿.md` **§十六** 为唯一权威源。

> **一句话**：对 A3 的模块划分方案（14 模块）做 **10 组不同角度**的对抗性检查。
> **检查者**：AI（对抗视角）｜ **日期**：2026-09-20
> ⚠️ **方法说明**：每轮**换一个角度**（不是重复同一角度 10 遍）——否则第 3 轮后就退化为噪音。

---

## 轮 1 · 职责单一性（每个模块是否只干一件事）

**查法**：逐个模块，数它承担了几个**不同的职责**。

| 模块 | 职责数 | 判定 |
|---|---|---|
| `app/main_window` | 1（框架/导航） | ✅ |
| `app/scene3d` | 1（3D 渲染） | ✅ |
| `app/dashboard` | 2（总览 + 数据表） | ⚠️ 可接受（都是"看板"） |
| `app/dialogs` | 1（弹窗） | ✅ |
| `core/program` | 2（程序模型 + 校验） | ⚠️ 可接受（校验是程序的附属能力） |
| `core/execution` | 2（运行控制 + 工艺参数） | ⚠️ 可接受 |
| `core/vision` | 1 | ✅ |
| `core/error` | 1（误差归正） | ✅ |
| **`core/device`** | **5**（设备清单 + 状态机 + 坐标映射 + 报警判定 + 统计计算） | 🔴 **垃圾桶** |
| `comm/interface` | 1 | ✅ |
| `comm/modbus` | 1 | ✅ |
| `data/store` | 1 | ✅ |
| `data/log` | 1 | ✅ |
| `infra` | 1 | ✅ |

### 🔴 发现 1（严重）：`core/device` 是垃圾桶

它把 `A2` 里"跨层拆剩的 5 个职责"全塞进去了：设备清单 / 状态机 / 坐标映射 / 报警判定 / 统计计算。

⇒ **这 5 件事毫无共同点**（一个是清单、一个是状态机、一个是几何计算、一个是规则判断、一个是聚合）⇒ **必须拆**。

## 轮 2 · 依赖方向（有没有环、有没有"下层调上层"）

**查法**：假设依赖方向为 `app → core → comm / data`，看有没有**反向**。

| 潜在反向依赖 | 问题 |
|---|---|
| `core/device` 含**报警判定** ⇒ 报警要触发 UI 提示 | 🔴 **core → app 反向** |
| `core/device` 含**坐标映射** ⇒ 但它服务于 `app/scene3d` | ⚠️ 算正向（app 调 core），但**语义上映射属表现** |

### 🔴 发现 2：报警判定放在 core，会造成反向依赖

"什么算报警"（判定）是业务，但**判定完要通知 UI**。若通过回调/信号（Qt 信号槽）则正常；若直接调 UI 就是反向。

⇒ **必须在架构里写明"用信号/事件向上通知，core 不得 include UI 头文件"**（这是 A4 接口设计要定的）。

## 轮 3 · 需求覆盖（127 条是否都有归属）

**查法**：逐类核对。

| 类 | 条数 | 归属 | 判定 |
|---|---|---|---|
| 功能域 `D*` | 88 | 各模块 | ✅ |
| 补充域 `N*` | 24 | 各模块 | ✅ |
| **`F` 非功能** | 8 | **未写明落点** | ⚠️ |
| **`X` 结构** | 3 | **无代码归属**（流程要求） | ✅ 正常 |
| **`REQ-ARCH`** | 9 | **未写明落点** | ⚠️ |

### ⚠️ 发现 3：需要一张「约束 → 落点」表

`F`（非功能）和 `REQ-ARCH`（架构冗余）是**约束**，不属任何单模块，但**必须有明确落点**，否则实现时会漏。

⇒ **缺失**：应补一张"约束 → 落在哪些模块"的映射表。

## 轮 4 · 耦合度（模块间依赖对数量）

**查法**：数每个模块被多少模块依赖。

| 模块 | 被依赖数 | 判定 |
|---|---|---|
| `core/device` | **5+**（scene3d / dashboard / execution / stats / alarm） | 🔴 **过高** |
| `core/program` | 3（execution / scene3d / dashboard） | ⚠️ |
| `comm/interface` | 2（execution / device） | ✅ |
| `data/store` | 2 | ✅ |

### 🔴 发现 4：`core/device` 被 5+ 个模块依赖

**被依赖越多，改它的风险越大** —— 这与轮 1 的"垃圾桶"是同一个根因的另一个投影。

---

## 轮 5 · 变更影响面（改一个功能要动几个模块）

**查法**：挑几个**关键功能**，数它散布在几个模块。

| 功能 | 散布在 | 判定 |
|---|---|---|
| **急停**（`REQ-RUN-004`） | `core/execution`（RUN-004）+ `core/device`（状态机 `REQ-STA-002`） | 🔴 **切两半** |
| **归正**（`REQ-ERR-004`） | `core/error`（算法）+ `comm/*`（下发）+ 独立单元（执行） | ⚠️ 正常（跨层必须） |
| **误差告警**（`REQ-ERR-006`） | `core/error` + `core/alarm` + `data/log` | ⚠️ 正常 |

### 🔴 发现 5：急停逻辑被切成两半

`REQ-RUN-004`（急停本地优先）在 `core/execution`，而 `REQ-STA-002`（急停可从任意状态进入）在 `core/device` 的状态机里。

⇒ **"急停"这个功能要改两个模块** ⇒ 边界切错了。

---

## 轮 6 · 与既有约束的一致性

**查法**：核对 S-1/S0 已裁的约束（`B-*`）是否有明确落点。

| 约束 | 应有落点 | 现状 |
|---|---|---|
| `B-017a` 状态机 = 层次 + 表驱动 | 状态机模块 | ⚠️ 在垃圾桶里，没独立 |
| **`B-017b` 每设备一线程 + SPSC 无锁汇聚** | **线程/并发模块** | 🔴 **无归属** |
| `B5` 虚拟下位机独立进程 | 独立单元 | ✅ |
| `B-010` 通信抽象层 + 现成库 | `comm/interface` + `comm/modbus` | ✅ |
| `REQ-INF-008` 构建环境（全用 vcpkg） | `infra` | ✅ |
| `REQ-DEV-003` 状态汇聚（单一事实源） | 设备模块 | ⚠️ 在垃圾桶里 |

### 🔴 发现 6：`B-017b`（线程架构）**没有归属模块**

这是本项目**最硬的技术点**（你简历上的"多线程并发"卖点），却在模块划分里**找不到家**。

## 轮 10 · 反面用例（按这套做，会在哪里痛）

**查法**：假设已经按这套开工，预判**最先撞到的 3 个痛**。

| # | 痛 | 根因 |
|---|---|---|
| **痛 1** | 改 `core/device` 时战战兢兢（5 个模块依赖它） | 轮 1/4 的垃圾桶问题 |
| **痛 2** | 改"急停"要同时改两个模块，容易漏 | 轮 5 的切分错误 |

### 🔴 发现 10：三痛同源

⇒ **都指向同一批修正**（拆垃圾桶 + 急停归一 + 线程归位）。
