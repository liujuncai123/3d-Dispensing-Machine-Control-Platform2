## 一、模块定位与落点论证

### 1.1 结论

| 项 | 结论 |
|---|---|
| **模块名** | **`app/replay`** |
| **层**（依 `S1-架构基线草稿.md` §十六 · §17.5） | **UI 层**（`app/main_window` · `app/scene3d` · `app/dashboard` · `app/dialogs` **+ `app/replay`**） |
| **ISO 23247 四域**（§14.6） | **④ 用户域** ——「**人看到与操作的部分**」 |
| **性质** | **独立模块**（不并入任何现有模块） |
| **模块计数影响** | **24 → 25**（`§十六` 是模块计数的唯一权威源 ⇒ **该变更属 S1 层新增内容，须用户裁决，见 §八 Q1**） |

### 1.2 为什么必须是**独立模块**（**4 条架构理由**，不是"因为用户说独立"）

| # | 理由 | 依据（原文） | 若不独立的后果 |
|---|---|---|---|
| **①** 🔴 **回放是"第二个事实源"，必须被显式隔离并互斥** | 运行时设备状态的唯一持有者是 `core/device`（§五 硬约束①）。回放要按时间轴**重演状态与坐标**，若把它塞进 `core/execution` 或 `app/scene3d`，就会出现"**同一时刻有两个当前坐标**" ⇒ 直接违反 `REQ-DEV-003`（单一事实源）与 §八 约束 4 | `S1-架构基线草稿.md` §五 硬约束①「`core/device` 是**设备状态的唯一持有者**；`core/concurrency` 只投递不持有」· §八 约束 4 | 列表显示实时状态、3D 显示回放状态 ⇒ "**显示三种、存储一份**"（`REQ-MON-001` 异常栏）被破坏 |
| **②** 🔴 **放 `core` 必然触发禁边** | 回放**必须驱动 UI**（3D + 数值表）。若 `app/replay` 改为 `core/replay`，则 `core/* → app/*` 直接命中禁边；若改用 `infra/eventbus` 迂回，语义也是反的 —— 依决策 17，eventbus 是「**底层有事往上通知**」，而回放是「**上层往下驱动**」 | `S1-#5依赖图方法-定稿.md` §五 禁边清单「`core/* → app/*` ｜ `§17.1` 主干③④⑤」；`S1-架构基线草稿.md` §17.2 决策 17「模块间通知走 `infra/eventbus`（`core` 绝不依赖 `app`）」 | 要么破禁边，要么把事件通道用反（两层语义混用） |
| **③** **放 `data/store` 会让它承担"时间轴语义"** | `data/store` 是存储层，职责是"存 + 取"；回放要的是"**按时间轴驱动呈现**"（时钟 / 倍速 / 播放状态机）。塞进存储层 ⇒ 存储层要认识播放状态与倍速 | §五 数据所有权表「**记录（含误差日志）** ｜ 唯一持有者 `data/store`」· §17.5 存储层铁律「**单写者 + 串行化**」 | 存储层被污染；回放的播放状态无处安放 |
| **④** **"与实时路径互斥"需要一个唯一仲裁者** | 回放期间，实时坐标仍在从 `comm/interface` 上来并写入 `core/device`。**谁来决定"现在显示哪一个"**？若散在 `app/scene3d` 与 `app/dashboard` 各判一次 ⇒ 两处判断不一致（违反 §五 硬约束③「视图不缓存…每次读同一份」） | §五 硬约束③「**视图不缓存**，每次读同一份（`core/device`）」；§八 约束 6 | 3D 在回放、表格在实时 ⇒ 界面自相矛盾 |

### 1.3 为什么**不放**另外三处（逐条否掉）

| 候选 | 否掉的理由 |
|---|---|
| **`core/execution`** | 🔴 **安全红线**：`core/execution` 是**下发执行**域（`REQ-RUN-001~010` · `REQ-PRM-*`）。回放若在其内，历史数据被当作"待执行程序"下发出去是**本项目最大的单点风险**（违反 `P-5`）。⇒ 见 §四 H-2 硬约束 |
| **`app/scene3d`** | `app/scene3d` 是**渲染器**（`REQ-3D-001~013`）。塞进回放 ⇒ 它同时持有"实时坐标源（`core/device`）"与"历史坐标源" ⇒ **理由①的事实源冲突**；且 `app/dashboard`（数值表）也要回放 ⇒ 会被复制一份回放逻辑 |
| **`data/store`** | 见理由③ |

## 二、接口清单（**5 个 `I*` 抽象接口** + 数据类型）

> **设计约束**：① 纯虚基类，**不含 Qt / VTK 头**（依 §五 禁边「核心/通信/数据 → 第三方库」的精神；`app/replay` 属 UI 层可用 Qt，但**接口头本身保持无依赖**，便于单测与替换）② 字段名依 `REQ-DB-005`（同一含义不出现两种字段名）③ 状态取值**复用 `REQ-STA-001` 的 8 态枚举**（`REQ-DB-005` 判据③）。

### 2.1 数据类型（`app/replay/api/replay_types.h`）

```cpp
// 状态机状态（播放器自身；与 REQ-STA-001 的 8 态设备状态是两个维度，不得混用）
enum class ReplayStatus { Idle, Loading, Ready, Playing, Paused, Finished, Error };

struct ReplayFrame {
    qint64  tMs;            // 相对回放区间起点的时间（ms）      —— 见 G-7（时基待定）
    QString deviceId;       // 设备标识（REQ-DEV-001 口径）
    bool    hasCmdPos;      // 该帧是否有预期坐标（空行程段为 false）
    Vec3    cmdPos;         // 预期坐标（REQ-LOG-007「预期坐标」）
    Vec3    actPos;         // 实际坐标（REQ-LOG-007「实际坐标」）
    DeviceState state;      // 复用 REQ-STA-001 的 8 态枚举（REQ-DB-005③）
    bool    glueOn;         // 🔴 预留字段：当前无数据源 ⇒ 恒 false（缺口 G-2）
    double  devUm;          // 偏差量（REQ-LOG-007）
    bool    overThreshold;  // 是否超阈值（REQ-LOG-007）
    bool    corrected;      // 是否已归正（REQ-ERR-006 记录字段）
    qint32  primitiveIndex; // 🔴 预留字段：当前无数据源 ⇒ -1（缺口 G-6）
};
struct ReplayRange      { qint64 beginMs; qint64 endMs; };
struct ReplaySourceDesc { QString kind; QString locator; };  // kind = "sqlite" | "csv"（P-3：导入器可替换）
```

> 🔑 **`glueOn` / `primitiveIndex` 两个"恒缺省"字段是本次预留的关键**：它们把 `S1-回放-数据支撑性分析.md` 的 **G-2 / G-6** 缺口**在接口层先占位** ⇒ 将来补数据时**不改接口、不改调用方**（满足 `P-3`「换实现不改调用方」）。

### 2.2 五个 `I*` 接口

```cpp
// ① 数据源抽象（P-3：换实现不改调用方；覆盖"SQLite 直读"与"导入文件"两条路径）
class IReplaySource {
public:
    virtual ~IReplaySource() = default;
    virtual Result       open(const ReplaySourceDesc&) = 0;
    virtual void         close() = 0;
    virtual ReplayRange  range()   const = 0;   // 回放区间（对应用户说的"一段时间的数据"）
    virtual QStringList  devices() const = 0;   // 该区间涉及哪些设备
};

// ② 按时间轴取帧（对应缺口 G-5：现有需求只有"列表检索"，没有"逐帧有序取数"）
class IReplayFrameReader {
public:
    virtual ~IReplayFrameReader() = default;
    virtual qint64                     frameCount()    const = 0;
    virtual std::optional<ReplayFrame> frameAt(qint64 i) const = 0;
    virtual qint64                     seekByTime(qint64 tAbsMs) const = 0;  // 时间 → 帧序号（二分）
};

// ③ 时钟 / 节拍（倍速）
class IReplayClock {
public:
    virtual ~IReplayClock() = default;
    virtual void   start(qint64 tickMs) = 0;
    virtual void   stop()  = 0;
    virtual void   setSpeed(double) = 0;   // 1.0 = 1:1；档位可配（REQ-INF-006）
    virtual double speed() const = 0;
};

// ④ 呈现侧接收（依赖倒置：app/replay 不认识 VTK/Qt 部件，也不认识渲染管线）
class IReplaySink {
public:
    virtual ~IReplaySink() = default;
    virtual void onFrame(const ReplayFrame&) = 0;
    virtual void onStatus(ReplayStatus)      = 0;
};

// ⑤ 播放控制（组合 ②+③，向 ④ 推帧；同时是"回放模式"的唯一状态来源）
class IReplayPlayer {
public:
    virtual ~IReplayPlayer() = default;
    virtual Result       load(std::unique_ptr<IReplaySource>) = 0;
    virtual void         play()  = 0;
    virtual void         pause() = 0;
    virtual void         stop()  = 0;               // ⇒ 退出回放模式，交还实时源
    virtual void         seek(qint64 tAbsMs) = 0;   // 跳转
    virtual void         setSpeed(double)    = 0;   // 倍速
    virtual void         step(qint64 deltaFrames) = 0;  // 单帧步进
    virtual ReplayStatus status() const = 0;        // 🔑 互斥仲裁的唯一来源（见 H-3）
    virtual void         attachSink(IReplaySink*) = 0;
    virtual void         detachSink(IReplaySink*) = 0;
};
```

### 2.3 与实时路径的互斥（**不新增第 6 个接口**，靠契约 + H-3 硬约束）

> **落点**：呈现实体（`app/scene3d` / `app/dashboard`）内部持有一个**数据源选择器**：
```cpp
enum class SceneSourceMode { Live, Replay };   // 定义在呈现侧，不属 app/replay 的接口
```
> **规则**：
> - `IReplayPlayer::status() != Idle` ⇒ `SceneSourceMode::Replay`，呈现层**丢弃** `core/device -> app/scene3d`（B 层）的实时事件；
> - `status() == Idle`（`stop()` 后）⇒ 切回 `Live`；
> - 🔴 **唯一仲裁者 = `IReplayPlayer::status()`** —— 不在两处各判一次（理由④）。

### 2.4 Qt 信号 / 槽对照表（实现侧可选，接口层不强制）

| 抽象接口成员 | Qt 侧对应（实现为 `QObject` 时） |
|---|---|
| `IReplayPlayer::play / pause / stop / seek / setSpeed / step` | `Q_SLOT void play();` …（由回放控制面板触发） |
| `IReplayPlayer → IReplaySink::onFrame` | `Q_SIGNAL void frameReady(const ReplayFrame&);` |
| `IReplayPlayer → IReplaySink::onStatus` | `Q_SIGNAL void statusChanged(ReplayStatus);` |
| `IReplayClock` 节拍 | `QTimer`（Qt 6 可用 `QChronoTimer`）`timeout` ⇒ `IReplayPlayer` 取下一帧 |
| 互斥广播 | `Q_SIGNAL void replayModeChanged(bool active);` ⇒ 呈现层据此切 `SceneSourceMode` |
| 线程归属 | 🔴 **回放播放器归属 UI 线程**（节拍靠 `QTimer`；取数若慢则异步拉取后回投 UI 线程）—— 依 `P-6`（线程架构先设计），**具体归属在 `#6 运行时视图` 定，不在本文拍** |

## 四、禁边检查与硬约束（**`P-5` 安全优先**）

### 4.1 🔴 禁边清单（`app/replay` 的**永不依赖**清单，7 条）

| # | 禁边 | 依据 | 违反后果 |
|---|---|---|---|
| **B-1** | `app/replay ⇸ core/execution` | `P-5`；回放是"只可视化" | 🔴 **把历史数据当新程序下发出去** —— 本项目最大单点风险 |
| **B-2** | `app/replay ⇸ core/device` | §五 硬约束①（`core/device` 是设备状态唯一持有者） | 回放帧写回运行时状态 ⇒ 实时与历史混淆，"重启后自动继续跑"类事故 |
| **B-3** | `app/replay ⇸ comm/interface` / `comm/modbus` | `REQ-COM-001`；回放期不得产生任何报文 | 回放触发真实下发 |
| **B-4** | `core/* ⇸ app/replay` | §五 禁边「`core/* → app/*`」 | 破坏"core 绝不依赖 app" |
| **B-5** | `infra/* ⇸ app/replay` | §五 禁边「`infra/* → 任何业务模块`」+ `§7.2.1`② | `infra/config` 反向依赖成环 |
| **B-6** | `app/replay ⇸ vtk` | 回放**不渲染**；渲染归 `app/scene3d` | 回放层被 VTK 绑死，失去"只供帧"的纯粹性 |
| **B-7** | `app/replay ⇸ E4（文件系统）` | `§14.2` E4：文件 API 由 `data/store` / `data/log` / `infra/config` 承担 | 第二个模块直连文件系统 ⇒ 与 `§14.5` 约束 2「E4 是共享资源 ⇒ 读写必须串行化」冲突 |

> ⇒ **B-7 的直接推论**：用户说的「**导入**一段时间的数据」，**导入也必须经 `data/store` 的导入接口**，不能由 `app/replay` 直接读文件。
> ⇒ 这也与 `P-3` 原文一致 ——「需真实数据或高成本的（… / **文件导入**）**只留接口**」。

## 六、最轻量实现（`P-3` + `P-4` 的平衡点）

### 6.1 边界怎么定

| 原则 | 要求 | 落到什么程度 |
|---|---|---|
| **`P-3`** | 「存在 `I*` 抽象接口 **+ 一个轻量实现**；换实现不改调用方」 | ⇒ **必须有 1 个能跑的轻量实现**（不能只有头文件） |
| **`P-4`** | 「不做'以后可能用到的完整版」；**留接口 ≠ 写实现** | ⇒ **不写** SQLite 查询 / CSV 解析 / 时间轴 UI / 倍速 UI / 回放帧持久化 |

### 6.2 最轻量实现 = **「空数据源 + 只走状态的播放器」**

| 件 | 内容 |
|---|---|
| **`NullReplaySource`** | `open()` 返回成功；`range()` = 空区间；`devices()` = 空；`frameCount()` = **0**；`frameAt()` 恒返回 `std::nullopt` |
| **`ReplayPlayer`（轻量实现）** | 实现**状态机与节拍**：`Idle → Loading → Ready → Playing/Paused → Finished/Error`；`setSpeed()` 生效；`seek()` 生效（无帧时 no-op，不崩）；**因无帧，`frameReady` 不发射** |
| **`app/scene3d` 的改动** | 只增加**一个可空成员** `IReplayFrameReader* replayReader_{nullptr};` + 一个 `setReplaySource()`；**`nullptr` = 实时模式** ⇒ **既有渲染路径零改动** |

### 6.3 DoD（**可判定**）

| # | 判据 |
|---|---|
| 1 | `app/replay/` 下 **≤ 6 个文件**（2 个 api 头 + `NullReplaySource` `.h/.cpp` + `ReplayPlayer` `.h/.cpp`） |
| 2 | 单测 **≥ 4 条且通过**：① `load(NullSource) ⇒ status()==Ready` ② `play() ⇒ Playing`，`pause() ⇒ Paused`，`stop() ⇒ Idle` ③ `setSpeed(2.0) ⇒ speed()==2.0` ④ `frameCount()==0` 时 `play()` **不发射** `frameReady` |
| 3 | `app/scene3d` 只多一个**可空指针**成员；`nullptr` 时行为与改动前**完全一致**（既有渲染路径零改动） |
| 4 | 边表按 §3.2 落 9 条（须先满足 P-1）⇒ `python 00-流程/check-deps.py` **退出码 0** |
| 5 | `app/replay` 目录内 **0 处** `QFile` / `std::fstream` / `core::` / `comm::` ⇒ 对应 H-4 / H-2（可 grep 验） |

### 6.4 "可讲清"的标准（面试一句话，**这是本设计的验收口径**）

> 「回放是**独立模块**：**数据源可替换**（直读 SQLite / 导入文件两种实现），**播放器只产出帧、不碰状态、不碰下发**；呈现层在**实时源与回放源之间切换**，切换的**唯一仲裁者是播放器的状态**；当前数据源是空实现，**换实现不改调用方**。」

> ⇒ 这句话同时覆盖：`P-3`（可替换 + 不改调用方）· 理由①（第二事实源隔离）· 理由④（唯一仲裁者）· `P-5`（不碰下发）。
