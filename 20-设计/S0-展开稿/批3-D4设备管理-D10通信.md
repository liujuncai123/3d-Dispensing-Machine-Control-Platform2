# 一、深度展开（8 条 · 10 字段）

## `REQ-DEV-001` · 设备列表可见

| 字段 | 内容 |
|---|---|
| **描述** | 系统应显示全部已配置设备，及其名称与当前状态。 |
| **验收判据** | ① 列表显示**全部**已配置设备<br>② 每台显示**名称 + 当前状态**<br>③ 选择某台 ⇒ 其余视图（3D / 程序 / 详情）**切换到该台** |
| **前置条件** | 至少已配置 1 台设备 |
| **异常 / 边界** | 设备数为 0 ⇒ 显示**空状态提示**（不得白屏）；设备较多时列表可滚动 |
| **依赖** | `REQ-STA-001`（状态集合）· `REQ-UI-001`（2D 主框架） |
| **来源** | S-1 §3（"需设备列表"） |
| **优先级** | **P0** |
| **可测性** | 演示 + 人工 |
| **状态** | ⏳ 待裁 |

## `REQ-DEV-002` · 设备「在线 / 离线」状态可见

| 字段 | 内容 |
|---|---|
| **描述** | 每台设备的在线 / 离线状态应可见，且状态变化时实时更新。 |
| **验收判据** | ① 每台显示在线 / 离线<br>② 断连后**在阈值内**变为离线（阈值见 `REQ-RUN-009`）<br>③ 恢复连接后状态**自动回到在线** |
| **前置条件** | — |
| **异常 / 边界** | "离线"与"报警"是**不同维度**（离线≠故障）⇒ 界面上二者不得混用同一标识 |
| **依赖** | `REQ-COM-003`（连接状态）· `REQ-RUN-009`（掉线即停） |
| **来源** | 子项 `S1`（状态可见性检查发现）· S-1 §3 |
| **优先级** | **P0** |
| **可测性** | **单测**（状态映射）+ 演示（拔线） |
| **状态** | ⏳ 待裁 |

## `REQ-DEV-003` · 状态汇聚（单一事实源）

| 字段 | 内容 |
|---|---|
| **描述** | 各设备状态应汇聚到一处，且各处展示（列表 / 详情 / 3D / 监控）**同一时刻取值一致**。 |
| **验收判据** | ① 同一设备在同一时刻，**列表与详情状态一致**<br>② 状态来源**唯一**（不出现两处各自维护）<br>③ 汇聚路径在并发下**不产生错序**（后发生的状态不得被先发生的覆盖） |
| **前置条件** | 多台设备在线 |
| **异常 / 边界** | **本条是并发正确性的核心** ⇒ 与 `B-017b`（每设备一线程 + SPSC 无锁汇聚）**直接相关**；需明确"汇聚点在哪、谁写谁读" |
| **依赖** | `B-017b`（线程架构）· `REQ-NFR-002`（多设备响应）· `REQ-DEV-002` |
| **来源** | S-1 §3（"需…状态汇聚"）· `B-017b` |
| **优先级** | **P0**（并发正确性） |
| **可测性** | **单测**（汇聚一致性）+ 演示 |
| **状态** | ⏳ 待裁 |

## `REQ-DEV-005` · 批量下发需二次确认

| 字段 | 内容 |
|---|---|
| **描述** | 对多台设备批量下发指令时，必须经二次确认才真正发送。 |
| **验收判据** | ① 选择 ≥2 台并下发 ⇒ **弹出确认**，列明**将影响的设备清单**<br>② 未确认 ⇒ **不发送任何指令**<br>③ 确认后 ⇒ 逐台下发并显示**逐台结果** |
| **前置条件** | 已选择多台设备 |
| **异常 / 边界** | 部分成功部分失败 ⇒ **必须逐台显示结果**（不得只报"成功"）；取消确认 ⇒ 状态**不变** |
| **依赖** | `REQ-DEV-004`（逐台下发）· `REQ-DEV-006`（故障隔离） |
| **来源** | `B-015`（安全边界：批量下发二次确认） |
| **优先级** | **P0**（安全） |
| **可测性** | 演示 + 人工 |
| **状态** | ⏳ 待裁 |

## `REQ-DEV-006` · 单台故障不扩散

| 字段 | 内容 |
|---|---|
| **描述** | 一台设备掉线或报错时，其余设备应不受影响，可继续运行。 |
| **验收判据** | ① 使 A 台掉线 ⇒ B 台**运行不受影响**<br>② A 台的故障**不产生对 B 台的指令**<br>③ A 台恢复后**不自动补发**此前未完成的指令 |
| **前置条件** | ≥2 台设备，其中 ≥1 台在运行 |
| **异常 / 边界** | 需澄清：故障台**是否应自动停机**？（建议：按 `REQ-RUN-009` 掉线即停，**但不停其他台**）⇒ **待你确认** |
| **依赖** | `REQ-RUN-009` · `REQ-DEV-003`（状态汇聚） |
| **来源** | `B-015`（安全边界：单台故障隔离） |
| **优先级** | **P0**（安全 + 差异化） |
| **可测性** | **单测** + 演示 |
| **状态** | ⏳ 待裁 |

## `REQ-COM-001` · 通信经抽象层

| 字段 | 内容 |
|---|---|
| **描述** | 业务代码不应直接依赖具体通信协议的实现，而应通过抽象接口访问。 |
| **验收判据** | ① 业务层代码中**不出现**具体协议 API（如 Modbus 库的类）<br>② 替换协议实现时**只改实现层**，业务层不变<br>③ 抽象接口**可被 mock**（供单测使用） |
| **前置条件** | — |
| **异常 / 边界** | 第 ③ 条是**可测性的前提**：接口不可 mock ⇒ 大部分通信相关单测无法编写 |
| **依赖** | `B-010`（抽象层 + 现成库）· `REQ-ARCH-000`（接口预留） |
| **来源** | `B-010`（用户裁：D 抽象层 + 现成库） |
| **优先级** | **P0**（架构亮点） |
| **可测性** | **单测**（用 mock 验证业务逻辑） |
| **状态** | ⏳ 待裁 |

## `REQ-COM-003` · 连接状态可见

| 字段 | 内容 |
|---|---|
| **描述** | 界面应显示每台设备的通信连接状态。 |
| **验收判据** | ① 每台设备显示"已连接 / 未连接 / 连接中"<br>② 状态变化**即时反映**<br>③ 与 `REQ-DEV-002` 的在线/离线**语义一致**（不得一处在线一处离线） |
| **前置条件** | — |
| **异常 / 边界** | "连接中"是**中间态**，需有超时上限（否则会永久停在"连接中"） |
| **依赖** | `REQ-COM-004`（掉线检测）· `REQ-DEV-002` |
| **来源** | 子项 `S2`（状态可见性检查发现） |
| **优先级** | **P1** |
| **可测性** | 演示 |
| **状态** | ⏳ 待裁 |

## `REQ-COM-004` · 掉线可检测

| 字段 | 内容 |
|---|---|
| **描述** | 通信中断应在阈值内被检测到，并触发既定处置（见 `REQ-RUN-009`）。 |
| **验收判据** | ① 拔线 / 停进程后，**在阈值内**判定为断连<br>② 判定后**触发** `REQ-RUN-009` 的停机逻辑<br>③ 检测机制**不依赖业务数据**（仅靠心跳或超时即可判定） |
| **前置条件** | 已建立连接 |
| **异常 / 边界** | **阈值未定**（建议 3× 心跳周期，由 S1 定）；网络闪断 ⇒ 应有一次重试机会（避免误判），**重试次数待定** |
| **依赖** | `REQ-RUN-009` · `REQ-COM-003` · **`B5`**（通信边界） |
| **来源** | `B-015`（"掉线 / 超时 ⇒ 停机"） |
| **优先级** | **P0**（安全） |
| **可测性** | **单测**（超时判定）+ 演示 |
| **状态** | ⏳ 待裁 |
